Why Do APIs Exist?

Before we touch any code, let's understand the problem APIs solve -- using something everyone knows.

Your Body Is Already an API System

You don't need to learn APIs — your body already runs on them. Every organ is a service, every nerve signal is a request, and every reaction is a response. Here's how:

👁
Eyes
work like
GET /api/vision
Your eyes send visual data to your brain. The brain processes it and returns "that's a car" — just like a GET request returns data.
🧠
Brain
works like
API Gateway
Your brain routes signals to the right organ, validates priorities, and decides what's urgent — exactly what an API gateway does with requests.
❤️
Heart
works like
Background Service
Always running, keeping everything alive. Like a server process that runs 24/7 handling requests without being asked.
💪
Muscles
work like
POST /api/action
Your brain sends a command: "move arm." The muscle executes it and sends back a status: "done." That's a POST request — you're creating an action.
🌡️
Skin (Nerves)
work like
Webhooks / Sensors
Touch something hot? Nerves instantly fire a signal without you asking. Like a webhook that triggers automatically when something changes.
🧬
Immune System
works like
Auth & Rate Limiting
Your immune system checks if something belongs (authentication), blocks threats (firewall), and fights off too many invaders at once (rate limiting).

The Point:

APIs aren't a foreign concept — they're the same pattern your body uses every second. A request goes in, it gets processed, and a response comes back. That's all an API is.

Section 02b

What an API Actually Is (and Isn't)

Before you go further, let's clear up three things that trip up almost everyone learning APIs for the first time.

🚪

Misconception: "An API is where the data lives"

An API is not the data. It's the door to the data. The data itself can live anywhere -- a database, a file, another API, or be generated on the fly. The API is just the agreed-upon way to ask for it and get it back.

Think of it like a restaurant:

You (app) → Waiter (API) → Kitchen (database, service, AI)

You never go into the kitchen. You don't know if the chef uses a gas stove or electric. You just talk to the waiter, place your order, and get your food. The API is the waiter -- not the kitchen, not the food.

📦

Misconception: "JSON is how APIs store data"

JSON is the packaging, not the storage. It's how the API wraps data for delivery. Behind the scenes, the same data might be stored completely differently.

Stored as → Sent as
Redis hash→{ "temp": 8.2 }
SQL database row→{ "temp": 8.2 }
CSV file→{ "temp": 8.2 }
Another API→{ "temp": 8.2 }
Calculated on the fly→{ "temp": 8.2 }

The user always sees JSON. They never know or care what's behind it. That's the whole point -- the API hides the complexity.

⚡

Misconception: "APIs need a server running 24/7"

Traditionally, yes. But modern serverless APIs (like the NAVADA API) work differently -- the function only exists while someone is calling it.

Traditional Server

Runs 24/7 whether anyone calls or not. You pay for uptime. You manage the machine. Always using memory and CPU.

Serverless (this API)

Function sleeps until called. Wakes in milliseconds, runs, returns data, dies. You pay per request. Nothing runs when nobody's asking.

To the user it feels identical -- the response comes back in milliseconds either way. The difference is what happens behind the scenes and what you pay for.

How a Non-AI App Uses an API vs How AI Uses It

Not all APIs are the same. The way your app consumes the response depends on whether the data is structured or generated by AI.

📊

Non-AI API (structured data)

GET /api/v1/weather?city=London
→ { "temp": 8.2, "condition": "Cloudy" }

Same request always returns the same shape. Your app knows exactly what fields to expect. You slot each value into a UI element: data.temp goes in the temperature box, data.condition goes in the status label.

Cacheable: Yes   Speed: Fast (ms)   Cost: Free/cheap
🧠

AI API (generated response)

POST /api/chat/send { "msg": "London weather?" }
→ { "reply": "It's 8C and cloudy..." }

Same question can return a different answer each time. The response is freeform text -- your app just displays it as-is. There are no fixed fields to parse, just a reply string that could say anything.

Cacheable: Rarely   Speed: 1-5 sec   Cost: Per token

The Takeaway

An API is a door, not a room. JSON is the language you speak through that door, not where things are stored. And the server behind the door might be always-on or might only wake up when you knock -- either way, you get your answer.

Important: Each tab is a different language

PowerShell code only works in Windows PowerShell. Python code only works in a Python terminal (python or python3). cURL (Mac) works in Mac/Linux Terminal. cURL (Windows) uses curl.exe in Command Prompt or Git Bash. 01

"What data do I have?"

A spreadsheet, a database, sensor readings, calculations, a list in a notebook -- anything.

How AI Actually Works: The Real Pipeline

Most people think an AI "does everything." That misconception exists because they don't see what's happening behind the scenes. Here's the truth: an LLM is just one part of a much larger system.

👤
User
Types a question or command
→
🌐
API Layer
Routes the request, checks auth, enforces limits
→
🧠
LLM
Reads the prompt, generates text — but cannot act
→
⚖️
Decision Logic
Code that interprets the LLM's output and decides what to do
→
🛠️
Tools / APIs
External services that actually execute the action
→
✨
Output
Result returned to the user

The Key Insight:

The LLM cannot browse the web, check stock prices, send emails, or read files on its own. It generates text that other software (APIs and tools) interprets and executes. The intelligence is in the orchestration — not in any single component.

A Real Example: "What's the weather in London?"

// What actually happens when you ask an AI assistant about the weather: Step 1 — User types: "What's the weather in London?" Step 2 — API Gateway receives the request, checks authentication Step 3 — LLM reads the prompt and generates: { "tool": "weather", "city": "London" } // ↑ The LLM does NOT know the weather — it decides WHICH TOOL to call Step 4 — Decision Logic parses the LLM output, validates the tool name & parameters Step 5 — Weather API (Open-Meteo) is called — this is where the REAL data comes from Step 6 — Output: "It's 12°C and cloudy in London" — assembled from API data, not LLM knowledge

Common Misconceptions vs Reality

Myth: "AI knows everything"

LLMs are trained on data up to a cutoff date. They don't have access to live information unless connected to external APIs that fetch real-time data.

Reality: APIs provide the live data

When an AI gives you a stock price, it called a Stock API. When it checks the weather, it called a Weather API. The AI decided what to ask — the API provided the answer.

Myth: "AI does all the work"

An LLM generates text. It cannot send emails, read databases, execute code, or interact with the physical world. Every action requires a tool or API.

Reality: AI is the brain, APIs are the hands

The LLM reasons about what to do. APIs and tools actually do it. Without the API layer, an LLM is just a very good text predictor with no way to act on the world.

Myth: "AI will replace developers"

AI can write code and answer questions, but someone has to build the APIs, the tools, the infrastructure, and the decision logic that makes the whole system work.

Reality: AI creates MORE demand for builders

Every AI system needs APIs to connect to. Every business using AI needs custom tools, data pipelines, and integrations. Understanding APIs makes you more valuable, not less.

Why This Matters for You

Understanding beats fear

When you understand the pipeline — User, API, LLM, Decision, Tool, Output — AI stops being a mystery. It's just software calling other software.

APIs are the real superpower

The LLM is impressive, but the APIs are what make it useful. Learning to build and use APIs means you can build AI-powered tools yourself.

Every AI product is an API product

ChatGPT uses APIs. Siri uses APIs. Tesla's autopilot uses APIs. Understanding APIs means understanding how every smart product actually works.

AI Caching: How to Cut LLM Costs by 80%

Every time an AI agent answers a question, it costs money. Tokens go in, tokens come out, and someone pays the bill. Caching is the engineering discipline that stops you paying for the same answer twice.

The Problem: Token Burn

An AI agent like ALEX runs 24/7. Every scheduled task, every user question, every tool call sends tokens to an LLM. Without caching, a production agent can burn $10-15/day repeating work it already did. Morning briefing? Full LLM call. Same stock question at 2pm? Another full call. Same system prompt sent 200 times? 200 full charges. This adds up to $300+/month for a single agent.

The Solution: Multi-Layer Caching

Caching works in layers. Each layer catches requests before they reach the expensive LLM. The more layers, the fewer tokens burned.

User Query(incoming request)
→
Response Cache(exact match?)
→
Content Cache(recent facts?)
→
Prompt Cache(static tokens)
→
LLM Call(last resort)
1

Layer 1: Prompt Caching

Every LLM call includes a system prompt (identity, rules, personality) and tool definitions (schemas for every available function). For ALEX, this is ~6,000 tokens repeated on every single call. Anthropic's prompt caching marks these static blocks so subsequent calls within 5 minutes pay only 10% of the token cost. One code change, 30-40% cost reduction on all calls. 

{
  system: [
    { text: identityPrompt, cache_control: { type: "ephemeral" } },
    { text: dynamicContext }
  ],
  tools: TOOLS  // 4,000+ tokens — should also be cached
}
2

Layer 2: Content Cache

ALEX generates a morning briefing at 8am using Sonnet ($3/1M tokens). At 2pm, you ask "how are markets?" The data hasn't changed. Instead of another expensive Sonnet call, inject the cached facts and let cheap Haiku ($0.80/1M) rewrite them naturally. Same quality answer, 90% cheaper. The trick: cache facts, not prose. Haiku writes fresh each time so ALEX never sounds robotic. 

// Cached facts (stored as JSON)
{ "topic": "FTSE 100", "value": "8,142", "change": "+0.3%", "age_hours": 6 }

// Haiku rewrites naturally each time
"The FTSE's up a third of a percent at 8,142 — steady day."
3

Layer 3: Response Cache

Some queries are identical: scheduled tasks run the same prompt daily, users ask the same questions. Cache the full response with a TTL (time-to-live). If the same query arrives within the TTL window, serve the cached response instantly. Zero LLM cost, zero latency. Set a 3-day max TTL and a 50-entry cap to prevent stale data piling up. 

{
  "query_hash": "a1b2c3",
  "response": "FTSE closed at 8,142...",
  "created": "2026-02-05T08:00:00Z",
  "ttl_hours": 72,       // auto-expires after 3 days
  "source": "morning-briefing"
}
4

Layer 4: Smart Model Routing

Not every task needs the most powerful model. A stock price check doesn't need Sonnet's reasoning. Inbox review doesn't need 16K output tokens. Route 80% of scheduled tasks to Haiku (4x cheaper) and reserve Sonnet for complex reasoning. Same result, fraction of the cost. 

Haiku  ($0.80/1M)  stock-alerts, inbox-review, check-followups
Sonnet ($3.00/1M)  morning-briefing, deep research, weekly review
Opus   ($5.00/1M)  complex analysis only (rare, explicit request)

The Diff Check: Only Burn Tokens on New Data

The smartest cache doesn't just store and serve — it checks for freshness before burning credits. Here's how it works in practice:

Day 1, 8am — Full Sonnet research call, cache the extracted facts
Day 1, 2pm — User asks about markets → cached facts found → Haiku rewrites ($0.001)
Day 2, 8am — Haiku quick-checks "any new data since yesterday?" via web lookup
    If new data → Sonnet call, update cache
    If same data → Haiku rewrites from cache ($0.001)
Day 3, end — Cache auto-expires → full refresh regardless (prevents stale data)

Real Impact: Before vs After

Before Caching
Daily token burn: ~200,000 tokens
Daily cost: ~$8-10/day (~$250/month)

Every call: full system prompt (2,000 tokens)
Every call: full tool schemas (4,500 tokens)
Every task: Sonnet ($3/1M tokens)
Heartbeat: 8 tasks/day x $0.02 each
Tool loops: 3x overhead per multi-tool request
Scheduled output: generated then discarded
After Caching
Daily token burn: ~50,000 tokens
Daily cost: ~$1.50-2/day (~$50/month)

Prompt cache: static tokens at 10% cost
Content cache: facts reused via Haiku
Model routing: 80% of tasks on Haiku
Tool loops: cached system prompt, no rebuild
Scheduled output: saved, indexed, reusable
3-day TTL: auto-cleanup, no stale data

Cache Hygiene: Keeping Data Clean

Hard TTL (3 days max)

Every cached entry auto-expires. No manual cleanup needed. Prevents stale data from accumulating. Financial data gets shorter TTLs (hours), static facts get longer ones.

Cache facts, not prose

Store structured data (numbers, dates, names), not AI-written paragraphs. The LLM rewrites fresh each time using cached facts, so responses never sound repetitive or robotic.

Cap the cache (50 entries)

Set a maximum number of cached entries. When the cap is hit, the oldest entry is evicted. This prevents the cache from growing unbounded and consuming storage.

The Takeaway:

Caching isn't about making AI dumber — it's about making it efficient. The AI still writes every response. It still reasons. It still uses tools. The difference is that it doesn't pay full price for information it already has. In production, this is the difference between a $250/month agent and a $50/month agent doing the same job.

What is an API in simple terms?▼

An API (Application Programming Interface) is a way for two programs to talk to each other. You send a request (like "What's the weather in London?") and get back structured data (like temperature, condition, humidity). Think of it like ordering from a menu — you don't need to know how the kitchen works.
