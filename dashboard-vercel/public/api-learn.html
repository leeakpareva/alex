Section 01

Why Do APIs Exist?

Before we touch any code, let's understand the problem APIs solve -- using something everyone knows.

Your Body Is Already an API System

You don't need to learn APIs — your body already runs on them. Every organ is a service, every nerve signal is a request, and every reaction is a response. Here's how:

👁
Eyes
work like
GET /api/vision
Your eyes send visual data to your brain. The brain processes it and returns "that's a car" — just like a GET request returns data.
🧠
Brain
works like
API Gateway
Your brain routes signals to the right organ, validates priorities, and decides what's urgent — exactly what an API gateway does with requests.
❤️
Heart
works like
Background Service
Always running, keeping everything alive. Like a server process that runs 24/7 handling requests without being asked.
💪
Muscles
work like
POST /api/action
Your brain sends a command: "move arm." The muscle executes it and sends back a status: "done." That's a POST request — you're creating an action.
🌡️
Skin (Nerves)
work like
Webhooks / Sensors
Touch something hot? Nerves instantly fire a signal without you asking. Like a webhook that triggers automatically when something changes.
🧬
Immune System
works like
Auth & Rate Limiting
Your immune system checks if something belongs (authentication), blocks threats (firewall), and fights off too many invaders at once (rate limiting).

The Point:

APIs aren't a foreign concept — they're the same pattern your body uses every second. A request goes in, it gets processed, and a response comes back. That's all an API is.

The Restaurant Analogy

You(Customer)
→
Menu(API Docs)
→
Waiter(The API)
→
Kitchen(Server / DB)
↓ Your Food (the Response) comes back through the Waiter
🍳

"You don't need to know how the kitchen works"

APIs hide complexity. You just ask for what you want and get a result back, without knowing the internals.

📖

"The menu tells you what's available"

API documentation lists every "dish" (endpoint) you can order, what ingredients (parameters) it needs, and what you'll get back.

📋

"You order in a specific way"

Requests follow a format: a URL, HTTP method, headers, and parameters. Like filling out an order slip.

📦

"You get exactly what you asked for"

The response is structured data (usually JSON) -- predictable, machine-readable, and consistent every time.

APIs You Already Use Every Day

🌦
Weather app on your phone → Weather API → forecast data
🚗
Google Maps in Uber → Maps API → routes & ETAs
💳
Card payment at a shop → Payment API → approved/declined

Status: 200 OK { "city": "London", "temp_c": 12, "condition": "Cloudy" }

HTTP Status Codes

200OK -- Success, here is your data
400Bad Request -- your mistake
401Unauthorized -- wrong/missing key
404Not Found -- endpoint doesn't exist
429Too Many Requests -- slow down
500Server Error -- not your fault

Example 1: Get a Stock Quote

const API_KEY = 'nav_your_key_here'; async function getStockPrice(symbol) { const res = await fetch( `https://alexnavada.xyz/api/v1/stock-quote?symbol=${symbol}`, { headers: { 'X-API-Key': API_KEY } } ); const data = await res.json(); if (data.data.error) { console.log('Error:', data.data.error); return; } console.log(`${data.data.symbol}: $${data.data.price}`); console.log(`Change: ${data.data.change} (${data.data.change_percent})`); } getStockPrice('AAPL');
import requests API_KEY = "nav_your_key_here" HEADERS = {"X-API-Key": API_KEY} def get_stock_price(symbol): url = f"https://alexnavada.xyz/api/v1/stock-quote?symbol={symbol}" res = requests.get(url, headers=HEADERS) data = res.json() if data["data"].get("error"): print("Error:", data["data"]["error"]) return d = data["data"] print(f"{d['symbol']}: ${d['price']}") print(f"Change: {d['change']} ({d['change_percent']})") get_stock_price("AAPL")

Section 05

How to Turn Anything Into an API

Every API starts with the same four questions. Master these and you can turn any data into a service.

01

"What data do I have?"

A spreadsheet, a database, sensor readings, calculations, a list in a notebook -- anything.

02

"Who needs this data?"

Your app, other developers, a dashboard, a phone widget, a chatbot -- identify the consumers.

03

"What questions will they ask?"

Design endpoints around the most common queries: "Give me today's X", "Search for Y", "Add a new Z".

04

"What format should answers come in?"

JSON is the standard. Design clear, consistent response objects with meaningful field names.

Key Principles

Start with questions, not data

What do you want to know? The question shapes what data you collect and how you expose it.

Structure beats volume

A well-designed small API is infinitely more useful than a messy big data dump.

Cache what doesn't change often

Yesterday's weather won't change. Cache it. Save costs and speed things up.

Document everything

Your future self (and others) will thank you. Every endpoint, parameter, and response field.

Version your API

/v1/ lets you evolve without breaking existing users. Always start with a version prefix.
